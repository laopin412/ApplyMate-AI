# ApplyMate AI — 概念資料模型（尚未定版）

> 這是**領域概念**，不是確定的 SQL schema；欄位名稱、資料型態、關聯、索引、資料庫種類皆待技術設計。

## 1. 核心資料實體

| 概念實體 | 可能包含的資訊 | 備註 |
|---|---|---|
| User / Account | 會員 ID、登入方式、Email 驗證狀態 | 密碼只由安全驗證機制處理；不要明文存放 |
| Profile | 五項基本資料與聯絡方式等 | 跨裝置會員資料 |
| Education / Achievement / Project / Skill 等 | 九大類中的可重複經歷 | 依種類決定關聯及欄位 |
| Application | 學校、科系、組別、狀態、備註 | 一個帳號可有多筆 |
| ApplicationEvent | 報名截止、面試、放榜、自訂事件與日期 | 用於提醒 |
| ApplicationStatusHistory | 時間、前狀態、新狀態、修改原因 | 申請歷程可追溯 |
| Document | 文件類型、適用學校／組別、版本、內容 | 草稿與正式版分開 |
| InterviewSession / Turn | 面試題目、回答、追問、改善建議 | 保存範圍尚待確認 |
| Reminder / Delivery | 事件、提醒時點、渠道、寄送／已讀狀態 | 防止重複寄送 |
| Draft / Revision | 草稿、正式資料版本、編輯時間 | 能恢復草稿、回溯重要修改 |
| ImportJob / ImportCandidate | 原始文件解析工作、候選資料、比對結果 | 使用者確認前不得正式寫入 |

## 2. 資料保存差異

- 訪客與未驗證 Email 會員：瀏覽器暫存；不可把此視為跨裝置長期儲存。
- 已驗證會員：本次 v0.1 不實作；未來後端階段在開發機資料庫；公開部署後移到**部署伺服器可持久化資料庫**；未來再視需求遷移至託管雲端。
- 原始上傳文件是否在匯入後保留，以及保存多久，**尚未定案**；以最少保存為預設建議。
- 所有會員資料查詢需具備伺服器端身分授權，避免 ID 猜測造成跨帳號讀取。

## 3. 合併與冪等設計建議

- 資料匯入及訪客併入應有唯一作業識別碼或指紋，避免重試時產生重複資料。
- 以「完全相同／疑似相似／衝突」分類；名稱相同不代表內容相同。
- 衝突資訊保存新舊版本，不自行丟棄；讓使用者最後決定。
- 備審文件及申請狀態等重要資料應有版本或修改歷程。

## 4. 隱私保護待辦

- 需要建立資料保留與刪除政策、備份與還原策略、上傳限制、隱私告知。
- 需要確認是否對 AI Provider 傳送完整個人資料，或只傳送完成任務必要欄位。
- 若對外正式公開，Email 服務與資料庫存放應考量安全性、可用性和防濫用。
